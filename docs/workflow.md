# Как работать над лабой

Кто что делает:

- **Вы:** даёте условие, отвечаете на вопросы, запускаете обучение сами или поручаете это Claude, правите выводы, сдаёте и защищаете.
- **Opus** (основная сессия Claude Code): разбирает условие, планирует, пишет спецификации, проверяет код, анализирует результаты.
- **lab-coder** (Sonnet): пишет код по спецификации Opus.
- **Mac:** код, проверки, ноутбук, лёгкое обучение. **PC (RTX 4090):** тяжёлое обучение.

Пример по всему гайду — лаба 1 «Нейронные сети для табличных данных»: `lab-1/task/task.md`.

## 0. Как передать условие

- Лучше всего PDF (в браузере: «Печать → Сохранить как PDF») или текст в `.md`. Лаба 1: страница курса → PDF на 11 страниц, прочитан целиком.
- Скриншот длинной страницы при передаче сжимается. Первый вариант условия лабы 1 был скриншотом 197×2000 px: читались только заголовки. Скилл не додумывает текст, а просит PDF.
- Файл кладите в `lab-N/task/`. Из `~/Downloads` Claude читать не может: это закрыто защитой macOS.

## 1. Старт: `/new-lab N`

```
/new-lab 1 lab-1/task/lab-1.pdf
```

1. Разбор условия (`/plan-lab`): полный текст → `task/assignment.md`.
2. Интервью: до 4 вопросов о том, что условие оставляет на ваш выбор. У каждого вопроса есть рекомендация.
3. План этапов → `task/task.md`. По нему работают агент, остальные скиллы и вы. `/kva-sync` переносит его на доску kvatask: эпик лабы и задача на каждый этап. Источник истины — `task.md`, доска только показывает его. Чтобы изменить задачу, правьте `task.md` (или попросите Claude), затем `/kva-sync`.
4. Каркас лабы, uv-окружение, заготовка ноутбука по разделам условия.

Условие изменилось или вышла новая часть: `/plan-lab N` обновит план и сохранит отмеченные этапы.

### Пример: лаба 1

Интервью и ответы:

| Вопрос | Ответ |
| --- | --- |
| Какие части делаем (дедлайн завтра, штраф 1 %/день)? | Максимум: части I и II, по две архитектуры |
| Какой датасет (п. 1.1)? | Wine Quality, как в прошлом семестре, чтобы сравнить результаты |
| Какие две архитектуры из учебных (п. 1.3)? | FT-Transformer + GANDALF |
| Как совместить `FAST_MODE` и «Run all» с нашим флоу? | Наш флоу: ноутбук читает `runs/` |

Что Opus проверил и решил сам. Всё записано в «Решения» `task.md`, ничего не принято молча:

- Ссылка на датасет вела на WineQT (1143 строки). В ml-2 ЛР1 был UCI red (1599 строк). Взят тот же UCI и тот же test (320 объектов), поэтому прошлые test-метрики сравнимы напрямую.
- Задача и метрики взяты из ml-2 ЛР1: классификация `quality`, F1 macro, balanced accuracy.
- Baseline — CatBoost с параметрами Optuna из ml-2 ЛР1. Это «сильная модель из прошлых лабораторных», которую разрешает условие.
- FT-Transformer и GANDALF подключаются через одну библиотеку `pytorch_tabular`: GANDALF есть только в ней.
- Категориальных признаков нет. Поэтому пункт условия «объект с неизвестной категорией» неприменим, вместо него взяты объекты вне диапазона train.

Этапы (`task.md`):

| Этап | Пункты | Баллы |
| --- | --- | ---: |
| 1. Данные, preprocessing, CatBoost baseline | 1.1–1.2 | 2 |
| 2. FT-Transformer и GANDALF «из коробки» | 1.3 | 2 |
| 3. Исследование гиперпараметров | 1.4 | 3 |
| 4. Сравнение, ошибки, importance | 1.5 | 3 (с этапом 5) |
| 5. Ручные объекты, часть I | обязательная проверка | — |
| 6. Протокол и подключение новых архитектур | 2.1–2.3 | 2 + 4 |
| 7. Обучение и исследование новых архитектур | 2.4 | 6 |
| 8. Итоговое сравнение и повтор ручных объектов | 2.5 | 3 |
| 9. Итоговые выводы и сдача | оформление | — |

Так выглядит этап в `task.md`:

```markdown
### [ ] Этап 2. FT-Transformer и GANDALF «из коробки» — п. 1.3, 2 балла
- Требование: две архитектуры в разумной базовой конфигурации (`assignment.md`, 1.3).
- В ноутбуке: 1.3 — идея каждой архитектуры; таблица: параметры, эпохи, val F1 macro, время, число параметров; кривые обучения.
- Как: `/code-lab stage 2` → `/train` → `/log-iteration` → `/write-conclusion`.
- Готово, когда: по рану на модель в `runs/`; smoke пройден; loss на старте ≈ ln 6 ≈ 1.79; одна batch переобучается.
- Результаты: —
```

Требования преподавателя для всей работы живут в разделе «Оформление и сдача» `task.md`, каждое — со строкой «В нашем флоу». В лабе 1:

- `FAST_MODE` = наш `SMOKE=1`. Smoke-раны не коммитятся.
- «Run all без ошибок»: ноутбук читает `runs/` и за секунды строит отчёт с теми же числами.
- Файл сдачи ≤ 10 МБ: размер проверяется после `/pack-submission`.

## 2. Этап за этапом

1. **Код:** `/code-lab all` берёт первый неотмеченный этап и после каждого ждёт вашего «дальше». Конкретный этап: `/code-lab stage K`.
   Внутри: Opus пишет спецификацию → lab-coder пишет код → Opus проверяет (ruff, ty, smoke, sanity-проверки, ревью диффа) → отчёт с разделом «Усложнения».
2. **Подбор гиперпараметров:** `/tune`, когда нужно подобрать lr или честно сравнить модели. В лабе 1 это этапы 3 и 7: сравнение архитектур честное, только если lr подобран для каждой.
3. **Обучение:** `/train` оценит время на Mac и посоветует машину. Команды — ниже. Если машина для всей лабы выбрана заранее (лаба 1 целиком на Mac), это записано в «Решениях» `task.md`, и `/train` сразу даёт команды для неё. Затем `/train` спрашивает, кто запускает обучение: вы или Claude. Claude запускает только на Mac, в фоне, и сам переходит к `/log-iteration`, когда обучение закончится. Так же работает `/tune`.
4. **Разбор итерации:** `/log-iteration` → `reports/iterations/vN.md` и `reports/results.md`.
5. **Выводы к разделу:** `/write-conclusion` пишет черновик `> **Вывод:**`, вы правите.
6. Этап отмечается `[x]` в `task.md`, когда выполнено его «Готово, когда». На доске его задача переходит в «в работе» при старте `/code-lab` и закрывается вместе с `[x]`. Задачу, добавленную на доску вручную, `/kva-sync` покажет и предложит взять в план.

Лаба 1, этап 1 целиком:

```
/code-lab stage 1      # src/data.py (загрузка, признаки, сплит), CatBoost в src/train.py, ячейки 1.1–1.2
/train                 # оценка времени, команда (например, uv run python -m src.train --run v1) и вопрос, кто запускает
/log-iteration         # reports/iterations/v1.md
/write-conclusion      # выводы к 1.1–1.2
```

## 3. Если код не нравится или в нём баг

- **Баг:** `/code-lab исправь: <симптом>`, например `/code-lab исправь: val F1 macro выше train с первой эпохи`. Opus воспроизводит баг, находит причину, исправляет через lab-coder и проверяет, что воспроизведение больше не срабатывает. Если баг испортил прошлые раны, называет, какие переобучить.
- **Не нравится:** `/code-lab перепиши <что> — <что не так и как хочу>`, например `/code-lab перепиши make_splits — хочу явные шаги вместо цикла`. Меняется только названное. Если переписывание лишь усложнит код, Opus скажет об этом до работы.
- **Сами:** правите код → `/code-lab review` → список проблем; исправления — по вашей просьбе. Чтобы агенты не трогали ваш код, пометьте его `# user-owned` (строка над `def`/`class`, первая строка файла или ячейки).

## 4. Выводы, сдача, защита

```
/write-conclusion      # «Итоговые выводы» — просмотр результатов и черновиков обязателен
/lab-review            # сверка с этапами task.md и «Оформлением и сдачей»; лучше в новой сессии (/clear)
/pack-submission       # единый ipynb → lab-N/submission/
/prep-defense          # вопросы к защите с ответами → reports/defense.md; /prep-defense quiz — тренировка
```

## Команды Mac и PC

Обучение на Mac:

```bash
cd lab-N && uv run python -m src.train --run v1
```

Обучение на PC: закоммитить и запушить код на Mac, затем на PC:

```bash
git pull && cd lab-N && uv sync
uv run python -m src.train --run v1
git add runs/v1 && git commit -m "run(labN): v1 — <суть>" && git push
```

Подбор гиперпараметров (на выбранной машине):

```bash
uv run python -m src.tune --study <имя> --trials N
git add runs/tune/<имя>.db && git commit -m "run(labN): tune <имя> — <цель>" && git push   # если на PC
```

После обучения на PC — на Mac:

```bash
git pull && cd lab-N && uv run python -m src.sync_mlflow   # ран с PC появится в MLflow на Mac
```
